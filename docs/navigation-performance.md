# J♡S 사진 전환과 캐시 수정

## v0.5.4 원인 분석

`EmbeddedPreview.extract`는 ARW를 메모리 매핑하고 TIFF/MakerNote의 최대 내장 JPEG 범위를 찾아 JPEG 데이터만 복사합니다. `ImagePipeline.decode`는 이 JPEG를 ImageIO로 디코딩한 다음 기존 ICC/Exif 규칙과 방향을 적용하여 sRGB 비트맵을 만듭니다. 이 파서와 색 변환 규칙은 변경하지 않았습니다. 현재 사진과 전체 화면/100% 확대는 같은 디코딩 이미지를 사용합니다.

직접적인 검은 프레임 경로는 `BrowserController.showPhoto`의 **캐시 미스** 분기였습니다. 새 비동기 요청 전에 `displayed = nil`, `viewer.canvas.decoded = nil`, `PreviewPane.select`의 `imageView.image = nil`을 실행했습니다. `PhotoCanvas.draw`는 배경을 검게 채운 뒤 decoded가 nil이면 반환하므로 잠깐의 미스도 검은 프레임이 됩니다. 기존 동기 캐시 적중 분기에는 이 nil 초기화가 없었습니다. 즉 이전에 본 사진이라도 캐시에서 밀려나면 같은 증상이 발생할 수 있습니다.

기존 일반 비트맵 캐시는 512MiB LRU였고 선택 사진 한 장은 별도로 고정했습니다. A7M4 내장 JPEG 7008×4672의 4바이트/픽셀 비트맵은 약 125MiB로, 일반 캐시에 약 4장밖에 남지 않습니다. 압축 JPEG 캐시는 64MiB에 더해 **4개 항목** 제한도 있었습니다. 약 5장 역탐색 시 두 단계의 캐시가 모두 비는 상황과 일치하는 코드 근거입니다. 사용자의 M1 Pro에서 실제 캐시 미스가 발생했다는 로그를 수집한 것은 아닙니다.

기존 프리페치는 앞뒤 한 장씩이었으며 retain 범위 밖 작업을 등록 목록에서 제거했습니다. 동기 디코더가 이미 실행 중이면 실제 실행을 중지할 수 없어, 빠르게 되돌아갈 때 아직 실행 중인 같은 파일의 새 작업이 생길 수 있었습니다. 기존 요청 식별자 검사는 오래된 UI 완료 결과를 이미 거르고 있었으며 이를 유지했습니다.

외장/내장 SSD 체감이 비슷하다는 관찰만으로 저장장치 병목을 배제하지 않습니다. 매핑·추출, JPEG 디코딩, 색/방향 변환, 큐 대기, UI 적용과 그리기를 분리해서 봐야 합니다.

## 실제 변경

- 다음 사진이 준비될 때까지 마지막 정상 비트맵을 유지합니다. 기존 HUD와 미리보기 세부 정보에 대상 파일명과 ‘읽는 중 · 이전 사진 유지’를 표시합니다. 실패해도 마지막 프레임을 유지하고 오류를 표시합니다. 이전 이미지 위에 현재 사진의 태그 표시가 겹치지 않게 합니다.
- 준비된 비트맵을 메인 스레드에서 한 번 교체합니다. 탐색 요청 식별자가 일치하지 않는 완료 결과는 적용하지 않습니다. 캐시 적중도 빈 프레임을 거치지 않습니다.
- 비선택 비트맵 LRU 예산은 물리 메모리의 1/8, 최대 1.5GiB입니다. 선택 비트맵은 UI가 이미 보유한 동일 객체로 따로 유지합니다. 압축 JPEG 캐시는 128MiB 바이트 한도로 관리하며 4장 제한은 제거했습니다. 실제 총 메모리에는 선택 이미지, 썸네일, 압축 JPEG, 실행 중 디코더의 임시 버퍼도 포함되므로 이 예산을 앱 전체 메모리 상한으로 부르지 않습니다.
- 시스템 메모리 warning/critical 시 비선택 비트맵과 압축 JPEG, 대기 중인 추측 작업을 해제합니다. 표시 중인 사진과 현재 사진의 완료 콜백은 유지합니다.
- 현재 방향의 다음 두 장을 먼저, 반대 방향 한 장을 뒤에 준비합니다. 표시용 foreground 작업은 한 번에 한 개만 실행합니다. 방향이 바뀌면 순서도 즉시 바뀝니다. 프리페치 큐는 한 작업만 실행하며 foreground 큐와 분리합니다. 대기 중 프리페치가 선택되면 같은 작업을 foreground로 승격합니다. 이미 실행 중인 작업은 등록을 유지하여 역탐색 요청과 공유합니다. 범위 밖 대기 작업과 이전 UI 구독만 취소합니다.
- 계측은 request→UI 적용, request→첫 새 프레임 draw 완료, 큐 대기, JPEG 소스 읽기/추출, ImageIO 이미지 생성 API, 지연 JPEG 디코딩을 포함한 기존 sRGB 래스터화, 디코더 전체 시간, 비트맵 캐시 조회, 캐시 보유 바이트 및 프로세스 RSS/peak RSS를 구분해 기록합니다. ImageIO는 생성 API가 반환된 뒤 실제 픽셀 접근 시 디코딩을 지연할 수 있으므로 생성 API 시간과 실제 JPEG 디코딩·sRGB 변환을 포함한 래스터화 시간을 구분합니다. shouldCache를 강제로 켜는 실험은 되돌리고 기존 ImageIO 옵션을 유지했습니다. 프레임은 새 캡션·태그 상태와 함께 그린 뒤 그리드 레이아웃과 프리페치를 처리합니다. Canvas는 실제 draw 호출 수·첫 이미지 이후 빈 draw 수·draw 소요 시간을 별도로 기록합니다. draw 콜백은 디스플레이에 실제 제출된 프레임/수직 동기 시각을 의미하지 않습니다.

## 검증 범위와 재현

macOS CI에는 실제 Sony A7M3/A7M4 샘플 두 개가 있습니다. 새 탐색 계측은 **실제 A7M4 한 파일을 12개 서로 다른 경로로 하드 링크**하여 키별 작업과 캐시의 working set을 검사합니다. 내용과 OS 파일 캐시는 공유되므로 실제 서로 다른 촬영 파일 12개 또는 콜드 디스크 I/O 측정이 아닙니다. M1 Pro 및 내장/외장 SSD 비교를 검증 완료라고 주장하지 않습니다.

M1 Pro에서는 동일한 실제 ARW 폴더에서 앱을 새로 실행한 뒤 최초 표시, 10장 순방향, 10장 역방향, 다시 순방향 10장 후 5장/10장 역탐색, 방향키 연타를 순서대로 확인해야 합니다. 기존 Console의 `dev.photoselect` navigation 로그에서 cacheHit와 latencyMs를 볼 수 있습니다. 화면 녹화로 검은 프레임과 마지막 사진 유지 시간을 별도로 확인하고, Activity Monitor의 앱 메모리를 함께 기록하세요. 같은 폴더를 SSD 간 비교할 때 OS 캐시 상태도 기록해야 합니다.

M1 Pro에서 이 수정본의 실제 캐시 적중률·전환 지연·RSS·검은 프레임 여부는 아직 측정하지 못했습니다.

수정 파일은 `Browser.swift`, `ImagePipeline.swift`, `Viewer.swift`, 해당 회귀/성능 테스트와 패키징 버전 설정입니다. J♡S 이름·공식 아이콘·로즈 UI·확대 좌표/입력·태그 JSON·필터·휴지통·폴더 접근 구현은 유지했습니다. 새 설치 파일은 이전 버전을 보존하기 위해 v0.5.5로 구분합니다.

비트맵 예산 1.5GiB는 **앱 전체 RSS 상한이 아닙니다**. 테스트 프로세스 RSS에는 프레임워크·썸네일·압축 소스·매핑·중간 버퍼·렌더링 자원도 포함됩니다. 같은 조건의 v0.5.4 전체 앱 RSS 대조 실험은 하지 않았으므로 메모리 사용량이 줄었다고 주장하지 않습니다. 캐시 보관량을 늘린 메모리/재탐색 속도 절충입니다. M1 Pro의 실제 RSS 및 메모리 압박 복구 확인은 남아 있습니다.

캐시 미스는 아직 느립니다. 최초 표시 5.20초, 처음 순방향 10장 27.53초는 그대로 보고하며, 이 경로가 100ms 이내라고 주장하지 않습니다. 처음 스캔의 미스 요청→적용 최대는 2045.72ms였습니다. 시나리오 총 시간에는 입력 함수, 명시적 redraw 및 완료 확인 대기도 포함됩니다. CPU draw 완료는 실제 디스플레이/GPU 프레젠테이션 시각이 아니며 화면 녹화 검증을 대체하지 않습니다.

Release의 완료된 디코더 표본 중앙값/최댓값:

ImageIO 생성 API의 짧은 시간을 순수 JPEG 디코딩 시간으로 해석하면 안 됩니다. 비용 대부분은 실제 픽셀을 그리는 단계로 지연됩니다. 기존 색 변환을 보존했으므로 그 단계의 JPEG 디코딩과 색 변환을 별도의 순수 시간으로 분리했다고 주장하지 않습니다. 캐시 미스의 CPU/프레임워크 비용과 큐 대기 지연은 추가 최적화 여지가 있습니다.

Debug도 빈 draw 0회, 캐시 적중 적용 최대 18.59ms였습니다. Release 캐시 적중 경로는 이번 CI 표본에서 100ms 목표를 충족했습니다. 미검증 실기기 항목에까지 이 결과를 일반화하지 않습니다.
